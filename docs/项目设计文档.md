## 一、项目背景

### 是什么

一个**单文件 HTML 预算执行看板**，帮助预算负责人（用户）管理年度预算的执行、预测、达标。

### 核心用户

- **维护者**：预算负责人（唯一编辑者），负责花钱和管理执行率
- **查看者**：BA（预算申请）、团队成员（局域网只读）

### 核心诉求（按优先级）

1. **看进展和风险**：当前执行率、预计年底、授予进度、在途冻结
2. **知道怎么做**：下个月 PO 下多少、从哪些钱包出、OD 调拨多少、还要催谁
3. **尽量无脑操作**：平台导出 Excel 丢进文件夹 → 打开看板 → 一切自动

### 约束

- **零部署**：不需要数据库、后端、云服务
- **Windows + Chrome**：内网环境，通过 git 仓库同步（只拉取不上传）
- **数据安全**：本地文件为唯一真源，清浏览器不丢数据

## 二、业务模型

### 三层结构

```
花钱项目（IT项目，×2）
  └─ 预算来源（考核维度，约十几个）   ← 同一个来源可以同时挂在两个花钱项目下，余额分开记
       └─ 费用类型
            ├── IT外包（走 PO）
            ├── 人力外包 OD（按月扣减）
            └── 自有人力（不管理，导入时忽略）
```

### 钱包：预算来源 × 花钱项目

平台里，一笔预算落到"某花钱项目下的某预算来源"，形成一个**钱包**：

- 钱包余额 = 执行表里该来源在该项目那一行、该费用类型的「剩余」
- 同一来源在两个项目下都有钱 = 两个钱包；**考核时按来源合并**算执行率
- PO 只能花对应项目下有余额的来源 → 指令必须指明"哪个钱包、出多少"
- OD 额度也按钱包记：调拨 = 同一钱包内 IT外包 → OD，扣减也从该钱包扣

### 五个视角

同一批钱从五个角度看，每个指标只属于一个视角，不能混：

| 视角 | 是什么 | 按这个维度算的指标 | 注意 |
|---|---|---|---|
| 花钱项目 | 平台导出的组织方式：每个项目一份总览、一份 PO 明细 | 钱包余额 | 执行表没有项目列，项目归属靠所在文件夹 |
| 预算来源 | 考核维度，可跨项目 | 执行率、目标、缺口、催 BA | 按来源合并，跨项目相加 |
| PO | 一张订单，按 PO 编号唯一 | PO 金额、状态、在途冻结、挂靠剔除 | 跨项目的 PO 出现在两个项目的明细里，PO 金额只算一次 |
| PO 行 | PO × 项目 × 来源，一行对应一个钱包 | 月度执行/预测、将执行、预计返还 | 行级金额可以直接相加 |
| 团队 | 人和单价 | 每月 PO 需求、OD 月额 | 与哪张 PO、哪个钱包付钱无关 |

### 预算来源的生命周期

```
年初规划（USD） → BA 申请 → 分笔授予（CNY） → 消耗（PO + OD） → 年底考核执行率
```

- **规划**：年初定，单位 **WUSD（万美金，保留小数）**，如 5.5 = $55,000
- **授予**：BA 申请后分笔到账，**全进 IT外包**；OD 用度需手工从 IT外包 调拨
- **考核**：执行率 = 已消耗 ÷ 规划×汇率；**每个来源有独立目标**（100%/92%/不考核/默认）
- **来源完全隔离**：A 的剩余不能给 B 补——B 缺钱要么催 BA（还没给），要么标失效（给不了了）

### PO（采购订单）

- **按自然月下达**：每月 20 号左右下下月 PO
- **一张 PO 可以跨项目**：可涉及多个花钱项目、多个预算来源，每个"项目 × 来源"一行；PO 金额是整张 PO 的总额
- **一个月通常下两张 PO**（原因与预算无关），两张合计才是团队当月的 PO 消耗
- **两类导出都按花钱项目**：每个项目导出一份"项目总览"（执行表）和一份"项目下 PO 明细"；跨项目的 PO 会同时出现在两个项目的明细里
- **冻结机制**：下单即冻结 → 执行中 → 验收（约 1 个月）→ 未花完的返还
- **跨年执行**：11 月 20 日前后下的 12 月 PO 是 12 月的服务，**计入今年**；12 月下旬用今年结余下的 1 月 PO 是 1 月的服务，**计入明年**，不算今年执行率
- **挂靠 PO**：别人用你的预算额度下的 PO，不属于你的管理范围（按 PO 编号整张标记剔除）

### OD（按月扣减）

- **扣减日历**（当月月底扣的金额，单位：月额）

  | 月份 | 1 月 | 2–5 月 | 6 月 | 7–11 月 | 12 月 |
  |---|---|---|---|---|---|
  | 扣减 | 0 | 各 1 | 2（上半年清算） | 各 1 | ≈3.5（11 月 + 12 月 + 年终奖） |

  12 月的倍数是参数 `bonusMonths`（估算，年底导入后校准）。1 月无扣减：12 月的费用已于 12 月 31 日扣完。
- **按钱包扣**：调到哪个项目、哪个来源的 OD 额度，就从那里扣
- **额度管理**：授予时全进 IT外包，OD 需手工调拨；一次调拨覆盖到下一个清算点（见 4.8），全年约 4 次
- **临时 OD**：年底为冲执行率临时增加 OD 人员，费用在 12 月 31 日一并扣除

### 关键口径

| 指标 | 定义 | 视角 |
|---|---|---|
| 执行率 | (IT外包已执行 + OD已执行) ÷ (规划WUSD × 10000 × 当年汇率) | 预算来源 |
| 总体目标 | Σ(规划_i × 目标_i) ÷ Σ规划_i（加权；不考核的来源按 0 计） | 预算来源 |
| 授予进度 | Σ可用预算 ÷ 年初规划 | 预算来源 |
| 可支配 | 各钱包的 IT外包剩余 + OD剩余之和。执行表的「剩余」已扣除全部在途 PO 预测，**不含冻结的钱** | 钱包 |
| 在途冻结 | Σ 每张 OPEN PO 的（PO 总额 − 该 PO 全部行的已执行） | PO |
| 预计返还 | 各 PO 行超出所属月的预测 + 当月多下（见 4.4） | PO 行 |
| PO 所属月 | 费用起始时间所在月份 | PO |
| 来源缺口 | max(0, 规划_i × 目标_i − 已执行_i − 将执行_i)；不考核的来源缺口为 0 | 预算来源 |
| 团队月 PO 消耗 | 当月所有 PO 行的执行合计（两张 PO 加起来） | 团队 |

## 三、数据源与导入

### 3.1 平台导出文件（每月 2 次，按年全量）

| 文件 | 内容 | 导入方式 |
|---|---|---|
| 项目总览 ×2（执行表，每个花钱项目一份） | 预算来源 × 费用类型的可用/执行/预测/剩余 | 按「快照日期 + 花钱项目」分别保存（累积） |
| PO 明细 ×2（每个花钱项目一份） | 花了这个项目钱的 PO 行：PO 编号/金额/状态/预算来源/月度执行与预测 | 覆盖式刷新 |
| 团队 Excel | PO/OD 页签，每行一人（姓名+单价，可选职级列） | 替换式（数据集为准） |

### 3.2 数据集文件夹：按花钱项目分子文件夹

执行表没有项目列，两个项目的导出文件名又相同，所以**项目归属靠文件夹**，不靠程序猜测：

```
数据集/                       ← 设置一次
├── 花钱项目A/                ← 子文件夹名 = 项目名或编号，自己起，定后不改
│   ├── 项目总览….xlsx
│   └── PO明细….xlsx
├── 花钱项目B/
│   ├── 项目总览….xlsx
│   └── PO明细….xlsx
└── 团队.xlsx                 ← 与项目无关的文件放根目录
```

规则：

- **项目归属 = 文件所在的一级子文件夹**。子文件夹名就是系统里的项目标识；以后多一个项目就多建一个文件夹
- 同一个项目的两类文件放同一个文件夹；旧文件可删可留，重复的自动跳过
- PO 行的项目以行内「IT项目名称」为准（为空时用所在文件夹）；文件夹与项目名称的对应关系从该文件夹里的 PO 明细自动学到，只用于显示
- 执行表不在项目子文件夹里（放在根目录，或松散文件拖拽导入）时没有项目归属：**不导入**，提示放进对应文件夹。拖拽整个文件夹会保留子文件夹信息，效果等同于数据集扫描
- 团队 Excel 等与项目无关的文件放根目录（放进子文件夹也能识别）
- 去重签名包含所在文件夹：同一个文件挪到另一个文件夹会被视为新文件，用于放错后的纠正

**安全网（只提醒，不拦截）**：每次导入后记下每个项目的"来源清单与可用预算"。新文件如果明显更像另一个项目，提示"疑似放反"，并说明把文件挪到另一个文件夹后重新导入即可覆盖。

**存储**：每个执行表快照保存两份视图——

- `rows`：按预算来源合并的视图（原有结构，趋势图、校验、备份照旧使用）
- `byProject[项目标识]`：按花钱项目分开的原始行（决策引擎用）

计算时每个项目取各自最新的一份。合并视图 = 各项目各自最新数据的合计（某次只导了一个项目的文件时，另一个项目沿用上一次，不会出现余额凭空变少）。

### 3.3 导入机制

- **数据集文件夹**：设置一次后，文件丢进对应子文件夹 → 打开看板自动扫描导入
- **文件类型自动识别**：PO明细（含 PO编码 列）、执行表（含 预算来源编码 列）、团队（含 人数+单价 或 姓名+单价 列）
- **快照日期 = 文件导出时间**（不是导入时间）
- **重复文件自动跳过**（按文件夹 + 文件名 + 大小 + 修改时间）
- **拖拽支持**：可一次拖多个文件或整个文件夹（含子文件夹）

### 3.4 PO 明细解析要点

- 动态月度列：`N月执行`（过去）/ `N月预测`（当月起），列头随导出月份变化；当前月 = 第一个"预测"列的月份
- **合并单元格兼容**：PO 级列（编号/金额/状态）可能纵向合并，续行为空 → 向下填充
- **跨项目的 PO 会重复出现**：一张 PO 用了两个项目的预算项时，两个项目的明细里都有它。PO 级字段（金额、状态、起止时间）按 **PO 编号**只取一次，不能相加；行级字段（预算来源、月度执行/预测）每个文件各管自己项目的行，直接相加
- **PO 金额列是 PO 口径**：整张 PO 一个数，在两个项目的明细里、在同一张 PO 的每一行上都重复同一个值。取一张 PO 的任意一行即可
- **同一 PO 下相同预算项的多行**：执行、预测都相加（在途冻结 = PO 总额 − 这张 PO 全部行的已执行合计）
- 挂靠剔除按 PO 编号整张剔除
- PO 台账按 PO 编号展示一行（总额、已执行、冻结、预计返还），可展开看各钱包的行
- **dimension 声明不完整兼容**：部分平台导出只声明到前几行，按实际单元格扩展范围
- 读取「IT项目编码」「IT项目名称」作为 PO 行的项目标识
- **月度列的含义**（已确认）：`N月执行` = 该 PO 下、该预算项（行）在 N 月执行了多少钱，是行级金额，可直接相加
- **三种状态**（已确认）：已关闭（CLOSED）的 PO，执行额是定稿；**往月的、未关闭的 PO**，已执行的金额是事实、不能调，能调的只是下单时各预算项的分配比例（即没花完的钱验收后退回到哪个预算项，见 4.14）；**当月及以后的 PO**，只有预测，各行加起来约等于 PO 金额，看不出执行了多少，按团队配置估算

### 3.5 执行表解析要点

- 两级表头：费用类型 → 子列（以前年度/本年度/可用/执行/预测/剩余）
- 自有人力列组自动跳过；合计行（编码为 `-`）自动跳过
- 各列含义：可用预算 = 累计授予（以前年度 + 本年度）；剩余 = 余额
- OD 剩余 = 可用 − 执行；IT外包 剩余 = 可用 − 执行 − 预测

### 3.6 团队 Excel 解析

- 页签名含 PO/OD 判断渠道
- 只读姓名 + 单价两列（可选职级列做组名），其余列忽略
- 同单价自动归组：组名 = 职级（如有）或 单价值
- 团队配置为**只读**（要改人改价 → 改 Excel → 重新导入）
- **PO 归属**（可选）：PO 页签里表头含"归属"的一列（如「PO归属」，值随意，如 PO甲 / PO乙）；或者单独一个页签名含"归属"的清单页签（姓名 + 归属两列，不带单价列），按姓名对应。用途见 4.7
- **变动计划**（可选）：页签名含"变动"或"计划"、且有年月列的页签，读六列——生效年月 / 结束年月（可选）/ 类型（PO|OD）/ 单价 / 人数（±）/ 备注。生效年月支持 2026-11、2026年11月、2026/11，只写 11 表示当年 11 月。规则见 4.5
- **PO 归属**（已确认的写法）：单独一个页签「po归属」，两列——姓名（PO 团队的人）、归属（两张 PO 的简称）。按姓名对应到 PO 页签里的人。也兼容在 PO 页签里直接加一列表头含"归属"的列。用途见 4.7

## 四、决策算法（核心）

### 4.1 设计原则

- **PO 金额 = 团队需求**，不是"补达标"——团队花不出超出能力的钱，多下的只会冻结
- **达标是结果，不是驱动力**——预计执行率是自然产出，不反向影响 PO 金额
- **一套推演**——把每个来源从现在推到年底，本月的指令是推演的第一步；摘要条、决策卡、行动清单、进展区用同一组数
- **集中**——一次下 PO 尽量只涉及 1~2 个钱包
- **少操作**——OD 调拨一次覆盖一个窗口，且只动一个花钱项目
- **指令先行**——卡片最上面是"这个月做什么"，推演明细折叠在下

### 4.2 月份分叉

| 决策点（每月 18–19 日导入后） | 本月要下的 PO | 卡片重点 |
|---|---|---|
| 2–10 月 | 下月 PO | PO 金额与钱包、OD 调拨、催 BA |
| 1 月（新年度） | 2 月 PO（1 月的 PO 去年 12 月已下） | 同上；1 月的 PO 在数据里显示为"当月在执行" |
| 11 月 | 12 月 PO（今年最后一笔） | 同上，并展开**年底推演**：达标来源数、临时 OD 补缺口、1 月 PO 能留多少 |
| 12 月 | 1 月 PO（下旬下，用今年结余） | 1 月 PO 金额与钱包、OD 年底清算额度、催验收返还 |

12 月是全年最关键的一张卡（下 1 月 PO），旧版代码在这个月没有卡片，属于缺陷。

### 4.3 数据口径

对每个预算来源 i（失效的不参与），用最新数据准备：

| 量 | 定义 | 来源 |
|---|---|---|
| 规划_i | WUSD × 10000 × 汇率 | 年初规划 |
| 目标_i | 数字 = 该来源目标；0 = 不考核；空 = 继承年度默认 | 年初规划 |
| 已执行_i | IT外包执行 + OD执行（截至上月，跨项目合计） | 执行表 |
| 将执行_i | 在途 PO 行中今年会执行掉的部分（4.4） | PO 明细 |
| 缺口_i | max(0, 规划_i × 目标_i − 已执行_i − 将执行_i)；不考核 = 0 | 计算 |
| 钱包余额 | 每个花钱项目 p 下的 IT外包剩余_{i,p}、OD剩余_{i,p} | 执行表「剩余」 |
| 可支配_i | 各钱包余额之和 | 执行表 |
| 预计返还_i | 该来源各 PO 行超出所属月的预测 + 当月多下 | PO 明细 |

平台上有钱但未关联规划的来源、规划了但平台未到账的来源，都列进推演表（分别标"未关联""未到账"），不遗漏任何一笔钱或缺口。

### 4.4 在途 PO 的三类处理

当前月 t = PO 明细里第一个"预测"列的月份；所属月 = 费用起始时间所在月。按 **PO 行**逐行判断：

| 情况 | 识别 | 所属月内的预测 | 超出所属月的预测 |
|---|---|---|---|
| 往月的 PO 还有钱 | 所属月 < t | 已变成执行列 | 全部算**预计返还**（验收后回钱包） |
| 当月在执行 | 所属月 = t | **将执行** = 该行按比例分到的 min(当月预测合计, 团队当月需求)；**多下** = 当月预测 − 将执行 → 预计返还 | 算预计返还 |
| 已提前下的 | 所属月 > t | 算**已下**：该月还要下的 PO 里扣掉；同时计入来源的将执行 | 算预计返还 |

- 执行表的「剩余」已把在途 PO 的预测全额扣掉，可支配里不含任何冻结的钱，**不需要再扣一次**
- 当月将执行计入来源的将执行_i，来源缺口随之变小，下月 PO 就不会重复往这个来源下
- 例：11 月两张 PO 的当月预测合计 58 万，团队 11 月需求 56 万 → 各行按 56/58 的比例计入将执行，合计 56 万；多下 2 万算冻结、12 月验收后返还
- 卡片列出识别结果（几张 PO、哪些来源、预计执行、多下），每月核对一眼
- 费用起始时间缺失时按"当月在执行"处理并标注"请人工确认"；挂靠剔除的 PO 不参与

### 4.5 团队需求与 PO 建议金额

```
某年月的有效人数(组) = 现在的人数 + 往将来看的变动 − 往过去看的变动
PO 日额_m    = Σ(PO 各组 该月有效人数 × 日单价)
PO 理论_m    = 日额_m × m 月工作日 × 出勤系数
校准系数 r   = 近 3 个实际月的「PO 实际执行 ÷ PO 理论」，限制在 0.9 ~ 1.1
               （不足 3 个实际月、或没有团队配置时 r = 1）
团队需求_m   = PO 理论_m × r
团队当月需求 = 团队需求_t            ← 用于 4.4 拆"当月在执行"的 PO
建议金额     = 团队需求_{t+1} − 已下_{t+1}，向上取整到千元
```

**变动计划**（团队 Excel「变动计划」页签，已确认）：

- **PO / OD 页签只写常驻人员**（现在在岗的）；临时人员不写进页签，只写在变动计划里
- 变动计划各列：生效年月 / 结束年月（可选）/ 类型（PO|OD）/ 单价（PO 填日单价，OD 填月单价）/ 人数（±）/ 归属（可选，只对 PO：归哪张 PO，值与「po归属」页签一致）/ 备注，按整月算。**PO 团队的进人和离场也写在这里**，类型填 PO
- 两种行：
  - **填了结束年月 = 临时人员**：只在 [生效年月, 结束年月) 这一段里算，和页签无关。结束年月填"不再算的那个月"（干到 12 月就填次年 1 月）
  - **没填结束年月 = 常驻人员的进出**：生效年月填成本归属月（到岗的月份；离场填离场后的第一个月）。用来还原过去月份的人数——往将来看，加上"现在之后到该月"生效的变动；往过去看，减去"该月之后到现在"生效的变动
- 一条常驻变动按"同类型 + 同单价"落到页签里**第一个**匹配的组上（两个组单价相同时不重复计入）；没有匹配组的，算一个虚拟组
- 例（已确认）：现在 11 月，OD 页签常驻 3 人（含 11 月新来的）。计划：`2026-10 ~ 2027-01 OD +1`（10 月来的临时，干到 12 月）、`2026-11 OD +1`（11 月来的常驻）、`2026-12 ~ 2027-01 OD +3`（12 月来的 3 个临时）→ 10 月 3 人、11 月 4 人、12 月 7 人、次年 1 月 3 人
- **OD 扣减的滞后不在这里处理**，由扣减日历决定用哪个月的人数（见 4.12）。上个月发生的常驻进出也要记一笔，否则最近一笔扣减会按现在的人数算；漏记时下次导入后用平台实际扣减额校准
- 校准（理论 vs 实际）只比"已有实际数的那几笔扣减"对应的月份，计划内的加减人不计为偏差
- 卡片上标注"已计入变动计划：…"；数据管理页列出计划和各月人数

- 没有团队配置（也没有变动计划）时：团队需求 = 近 3 个实际月的月均 × 工作日修正
- 已下_{t+1} = 所属月为 t+1 的 PO 行在 t+1 月的预测合计（4.4 第三类，几张 PO 一起算）；一个月分几次下 PO、或下完又导入一次时，卡片显示"已下 X / 还需 Y"
- 校准系数的作用：多下成了习惯时，建议金额自动收紧，冻结随之变少。页面同时显示理论、校准系数、近 3 月实际折算三个数
- **浮动参考**（只展示，不改变建议金额）：下限 = 需求 − 0.5 × 日额（请假多于加班）；上限 = 需求 + 1 × 日额（加班、加人）。11、12 月下 PO 时上限 = 需求（年底冻结的钱要到明年才回来，不多下）
- **1 月 PO 需求** = 明年 1 月的日额（含明年生效的变动） × 明年 1 月工作日 × 出勤系数 × r，按当前单价估算，新一年单价调整后重算

### 4.6 年底推演表

把每个来源从现在推演到 12 月 31 日。钱按下面的顺序使用（先硬性，后可选）：

```
① 团队 PO（硬性）    t+1 … 12 月每月的团队需求
② 常规 OD（硬性）    t … 12 月的 OD 扣减（按扣减日历）
③ 临时 OD 补缺口     仅年底：仍有缺口的来源
④ 1 月 PO            仅 11、12 月：用达标后的结余
⑤ 花不掉的剩余
```

- ①② 严格按月排：每个月先排"下月的团队 PO"（20 号前后下单），再排"当月月底的 OD 扣减"。近处的硬性支出先拿到钱；钱不够时 PO 先于 OD，OD 拿不到钱时明确提示"额度不够且无钱可调"
- 往月未关闭 PO 的**验收返还额**不用于本月的 PO（时效不可控），但年底（11、12 月）可以用于 ③ 临时 OD 和 ④ 1 月 PO——前提是 12 月 15 日前完成验收，卡片上会标注"需验收返还后才有"
- 另有一个**可选项**"改返还去向"（见 4.14）：往月未关闭 PO 的分配比例验收前可调，只影响没花完的钱退回到哪个钱包，不改变执行额

每个来源一行：

| 列 | 含义 |
|---|---|
| 后续 PO | ① 分到该来源的合计（本月的一份单独给出） |
| 常规 OD | ② 分到该来源的合计 |
| 临时 OD | ③ = min(该来源剩余缺口, 剩余可支配) |
| 1 月 PO | ④ 从该来源出的金额 |
| 年底预计执行 | 已执行 + 将执行 + 后续 PO + 常规 OD + 临时 OD |
| 预计执行率 | 年底预计执行 ÷ 规划，对比目标 → ✓达标 / ✗差多少 |
| 余量去向 | 留 1 月 PO / 花不掉 |

**汇总**：达标来源数 n/m、预计总体执行率、加权目标、1 月 PO 可留与缺口、花不掉金额、临时 OD 合计与约合人数。

规则：

- 进展区"预计年底" = 推演表合计 ÷ Σ规划。普通月不排 ③④，即"团队照常干、不额外加 OD"的结果
- **团队资金不足**：可支配合计 < ① + ② → 红色预警，并算出钱在第几个月耗尽
- **临时 OD** 约合人数 = 补缺口金额 ÷ OD 平均月单价（按整月计），需在 12 月清算前到岗
- **1 月 PO 缺口** = max(0, 1 月需求 − 可留)。可留 = ①②③ 之后各钱包 IT外包剩余的合计（OD 额度要先调回才能下 PO）。有缺口时提示：每调低某来源目标 ¥1，可留就多 ¥1。目标由用户权衡，系统只提醒、不改

### 4.7 PO 分配规则

把每月的建议金额分到钱包（来源 × 花钱项目）：

1. 候选来源按**缺口从大到小**排；不考核和已达标的来源排在最后，作为自由资金
2. 依次分：分配_i = min(缺口_i, 可支配_i − 已分配)
3. 来源选定后选它的一侧钱包：优先选余额够的那一侧（一个来源只动一个钱包）；两侧都不够时才两侧都下
4. 所有缺口都填满后还有余 → 从自由资金出，富余多的优先
5. 输出钱包分配，例如："合计 ¥56.3 万 ← P1/来源A ¥40 万、P2/来源C ¥16.3 万"

- 不按比例分摊；一次下 PO 尽量只涉及 1~2 个钱包
- **按人员归属分张**：团队 Excel 里每个人标了「PO归属」时，把当月的 PO 按归属拆成几张——各张金额 = 归属人员的 日额 × 工作日 × 出勤系数 × 校准系数（各自向下取整到千元，余数按小数部分从大到小补，保证合计不变）；钱包分配按顺序依次分给各张。变动计划里临时的 PO 人员可以在「归属」列填他归哪张；没填归属的并成一张
- 某钱包 IT外包剩余不够、但同来源 OD 剩余有钱时可以补，标注"需先把该来源的 OD 额度调回 IT外包"
- 推演表里后续各月（t+2 … 12）用同一规则依次分，只用于预测年底结果

### 4.8 OD 调拨规则

目标：全年调拨 4 次左右，每次只动一个花钱项目。

| 窗口 | 在哪个月的决策点调 | 覆盖到 |
|---|---|---|
| 1 | 1 月（或额度第一次不够时） | 5 月底 |
| 2 | 5 月 | 6 月底（含上半年清算） |
| 3 | 6 月 | 10 月底 |
| 4 | 11 月 | 12 月底（含年终清算） |

每个决策点都会核对：**本次调拨 = max(0, 到窗口末的扣减需求 − OD 剩余合计)**，结果为 0 就不提示。

**选花钱项目**（一个窗口只选一个）：

1. 优先选"仍有缺口的来源多、且这些来源的 IT外包剩余够整个窗口需求"的项目——OD 的执行顺便补缺口
2. 打平时选来源多的；再打平沿用上次（执行表里 OD 可用预算所在的项目）
3. 该项目不够才动另一个项目，并在卡片上标出

**选来源**：项目内按缺口从大到小。每个来源可用额度 = 已有 OD 剩余 + 可从同一钱包 IT外包 调入的部分（不超过它的剩余缺口）；缺口用完后才用自由资金的来源。

**输出**："OD 调拨 ¥X：花钱项目 P1 → 来源 A（IT外包 → OD），调后额度可用到年底清算"。

**收尾**：12 月决策点核对清算额度；清算后如有多余 OD 额度，提示调回 IT外包，否则年底花不掉。

### 4.9 催 BA

来源缺口 > 可支配 + 预计返还 时：

- 差额 = 缺口 − 可支配 − 预计返还
- 分类：规划了但平台没有这个来源 = **未授予**；有来源但可用预算不够 = **授予不足**；确定给不了 = 标**失效**
- 期限：若只靠 PO 消化（不动用年底临时 OD），最晚到账月 = 12 − ceil(差额 ÷ 月均团队 PO 需求)

### 4.12 预测模型与工作日

- **PO 需求（B主A兜底）**：有团队配置（或变动计划）时用理论 × 校准系数；没有时退回历史月均 × 工作日修正
- **OD 扣减**：有团队配置（或变动计划）时，每笔扣减按**费用所属月**的有效人数算，滞后自动体现——2–5 月、7–11 月的月底扣上个月的费用；6 月底 = 5 月 + 6 月的费用（上半年清算）；12 月 31 日 = 11 月 + 12 月 + （bonusMonths − 2）个月的 12 月费用（年终奖）；1 月无扣减。例：11 月底扣的是 10 月人数 × 单价。没有团队配置时用历史月均 × 倍数
- **校准提醒**：理论 vs 近 3 月实际偏差 > 10% → 提醒
- **工作日**：内置官方假日表（2026、2027 精确，含调休），其他年份用推算引擎，任何年份自动计算

### 4.13 在途与返还看板

PO 台账页，回答"验收后有多少钱、从哪张 PO、哪个预算项、退回到哪个钱包"：

- **按 PO**：一张 PO 一行（可跨多个花钱项目、多个预算来源）——PO 总额、已执行、在途冻结、其中将执行、验收后返还；下面列出它在每个钱包的冻结与返还
- **按钱包**（花钱项目 × 预算来源）：冻结、将执行、验收后返还、涉及的 PO
- **多下率**：往月「PO 总额 vs 实际执行」，当月为预估值；连续偏大说明习惯性多下，校准系数会自动收紧建议金额

冻结与返还分到各行的规则：往月 PO 以"超出所属月的预测"为权重，当月/提前下的以"所属月内预测"为权重；整张 PO 都没有预测时才用已执行额。没有 PO 金额列时，冻结退回按预测估算。

### 4.14 改返还去向（可选项，不是必做项）

平台口径（已确认）：**已执行的金额是事实，不能调**。往月的、未关闭的 PO，能调的只是下单时各预算项的**分配比例**（例如下单时 A/B = 3.5/1.5），也就是**没花完的钱验收后退回到哪个预算项**；PO 总额不变；已关闭的 PO 是定稿。

例：PO 下单 5 万，A 3.5 万 / B 1.5 万；实际 A 执行 3 万、B 执行 1 万。没花完的 1 万验收后返还，默认 A、B 各退 0.5 万；把比例改成 A 3 / B 2，则 1 万全部退回 B。执行额 3 万/1 万不变。

用户在执行中尽量避免这种调整，所以系统**只在能补上"来源缺钱"时提示**，不当作必做项：

- 只看**往月未关闭、有返还**的 PO
- **可让出的行**：该行所属来源用不上这笔返还——不考核的来源 = 全部返还；考核来源 = 返还里超出自己缺口（缺口 − 可支配）的部分；未关联规划的不让
- **想接收的行**：同一个 PO、同一个花钱项目内，"去掉可支配和今年能用上的返还后仍然缺钱"的来源，缺得多的优先
- 改过去的金额 = min(可让出, 接收方还缺的, 该行返还)
- 效果：只改变返还归属到哪个来源/钱包，进而影响"来源缺钱"的差额、年底的 ③ 临时 OD 和 ④ 1 月 PO；**执行额、缺口、本月 PO 分配都不变**

"今年能用上的返还"：往月未关闭 PO 的返还；当月 PO 多下的部分要到明年验收后才回来，年底（11、12 月）不算，普通月份才算。

输出：决策卡"可选：改返还去向"——PO 编号、多少钱、默认回到哪个来源、建议改到哪个来源；PO 台账对应行标注"建议从别的预算项改过来 / 建议改到缺钱的预算项"。

已确认：一张 PO 跨两个花钱项目时，只能在本项目的预算项之间改。

## 五、风险与预警

| 级别 | 类型 | 触发条件 |
|---|---|---|
| 🔴 | 团队资金不足 | 可支配 < 剩余团队 PO 需求 + 常规 OD 扣减 |
| 🔴 | OD 额度已不足 | 执行表出现"费用先结算至PO受益部门"且有金额 |
| 🔴 | 达标风险 | 推演后预计执行率 < 加权目标，或有考核来源未达标 |
| 🔴 | 两表不符 | PO明细汇总 ≠ 执行表（超过容差） |
| 🔴 | 编码未关联 | 平台出现新预算来源但未关联规划 |
| 🟡 | 授予落后 | 授予进度 < 时间进度 − 10pt |
| 🟡 | 来源缺钱 | 缺口 > 可支配 + 预计返还（催 BA） |
| 🟡 | 清算月 | 5 月/11 月，6 月/12 月 OD 大额清算将至 |
| 🟡 | 1 月 PO 缺口 | 11、12 月，达标后的结余不够 1 月需求 |
| 🟡 | 花不掉的余量 | 11、12 月，达标并留足 1 月后仍有大额剩余 |
| 🟡 | 在途冻结 | 预计返还 > 0，需催验收 |
| 🟡 | 团队校准偏差 | 理论 vs 实际偏差 > 10% |
| 🟡 | 人数待确认 | 超 35 天未确认团队人数 |
| 🟡 | 数据过期 | 超过设定天数未导入 |
| 🟡 | 文件放错位置 | 执行表不在项目文件夹里，或疑似放反 |
| ℹ️ | 跨年 PO | 1–3 月识别 1 月服务的 PO（去年 12 月下旬下单、用去年结余） |
| ℹ️ | 落账节奏 | 11–12 月提醒：冲今年执行率只能靠年内能执行完的 PO 和 12 月 31 日的 OD 清算 |

## 六、特殊处理

### 剔除机制（两级）

| 级别 | 对象 | 影响 | 恢复 |
|---|---|---|---|
| 预算来源级 | 整个预算来源 + 其所有 PO | 执行/可用/剩余全部不计 | 预算来源页恢复 |
| PO级（挂靠） | 整张 PO（按 PO 编号，含它在各项目下的行） | 从PO管理剔除，**已执行仍计入执行率** | PO台账恢复 |

### 失效标记

- **场景**：规划了但预算下不来（给不了了）
- **影响**：从执行率分母剔除、不再催BA
- **恢复**：随时可恢复

### 目标设置

| 值 | 含义 |
|---|---|
| 留空 | 继承年度默认目标（如95%） |
| 数字（如92） | 该来源独立目标 |
| 0 | 不考核（无目标线，缺口为 0，其余额是自由资金） |

### 同一来源挂在两个花钱项目下

- 余额分开记，考核合并算
- PO 和 OD 的指令都写明从哪一侧出，优先只用一侧

## 七、技术架构

### 持久化（文件写穿）

```
budget.json（仓库 data/ 目录）= 唯一真源
  → 每次变更自动写入（防抖800ms，原子写）
  → 随 git 同步，清浏览器不丢

localStorage = 缓存
  → 断连时兜底，重连自动同步
  → 顶部横幅显示连接状态
```

### 版本迁移

- schemaVersion 逐级自动迁移（v2 → v3 → v4）
- **迁移前自动备份**原始数据到 `budgetDash.autobak`
- **v4**：执行表快照增加 `byProject`（按花钱项目分开的原始行）和各项目的来源指纹。旧快照没有这一维时，合并视图照常工作；按钱包区分的指令在下次导入执行表后自动具备

### 分享机制（零部署）

```
维护端（双击打开 file://）：
  正常编辑，数据自动写 budget.json

查看端（局域网 http://IP:8734）：
  双击「启动分享.bat」→ PowerShell 静态服务
  同事浏览器打开 → 自动进入只读模式
  刷新即看最新发布的数据
```

- 发布 = 导出 data.json 放服务目录
- 团队单价默认**不包含**在分享数据中（敏感）
- localhost 永远走编辑模式（维护端不会误入分享模式）

### 数据集文件夹

- Chrome File System Access API
- 文件夹句柄存 IndexedDB，Chrome 记住授权
- 打开看板自动扫描新文件并导入；扫描时带上文件所在的一级子文件夹名（项目归属，见 3.2）

### 局域网共享

- `启动分享.bat` + `server.ps1`（Windows 自带 PowerShell，零安装零管理员）
- 端口 8734，窗口显示分享地址

## 八、历史数据与回测

### 设计思路

历史记录**挂在每次导入上**（不是"看页面"的时间点），因为导入 = 有新数据 = 有意义的检查点。

### 数据结构

```json
{
  "importLogs": [
    {
      "date": "2026-11-18",
      "advice": { "poNeed": 563000, "alloc": [["P1","A",400000], ["P2","C",163000]], "odXfer": 98000 },
      "estimates": { "curMonthExec": 560000, "curMonthOver": 20000, "odDecSettle": 315000, "janNeed": 630000 },
      "rollup": { "hitSources": 11, "sources": 12, "forecastRate": 0.932, "weightedTarget": 0.915 }
    }
  ]
}
```

### 下次导入时的对比

| 上次的估计 | 实际（来自新数据） | 用途 |
|---|---|---|
| 当月将执行 | PO 明细里该月执行列的合计 | 校准系数的输入 |
| 当月多下 | 这些 PO 行超出该月的预测合计（真正返还的） | 衡量"多下"估得准不准 |
| PO 建议金额 | 当月实际下达的 PO 预测 | 展示"建议 vs 实际" |
| 12 月 OD 清算额 | 执行表 12 月 OD 执行增量 | 校准 `bonusMonths` |
| 1 月 PO 需求 | 次年 1 月 PO 金额 | 校准跨年估算 |

### 对比展示

```
上次建议（11-18）vs 实际（11-30）：
  PO 建议 ¥56.3万 → 实际下达 ¥56.0万（偏差 -0.5%）
  当月多下 估 ¥2.0万 → 实际 ¥1.6万
  执行率预测 93.2% → 推演更新 92.8%（差 0.4pt）
```

### 长期价值

1. 用户能看到"上个月建议准不准"
2. 系统积累数据后可自动校准出勤、年终奖倍数
3. 年底复盘有据可查
